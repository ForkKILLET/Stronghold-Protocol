# 匿名个人档案与服务器战绩

## 使用

开启用户存储后，浏览器自动获得匿名档案，仍然直接输入昵称开始游戏。
主要入口是共享顶栏右侧的头像／昵称；开始页、大厅和等待室均打开同一个全屏「博士档案」，设置不再重复提供入口。
顶部展示个人头像、昵称与自动保存／暂未同步状态，下方为总览、策略、战斗累计、对局记录、个人资料和档案管理。
个人资料从原版个人头像库选择头像、修改昵称；档案管理提供恢复码与本机记录导入／导出／清空。头像和昵称在下一局完整生效；音量、画质、快捷键继续按设备保存在本机。
既有浏览器统计保留且不自动上传。总览／策略／战斗累计以服务器全部本人结算为准（并非只统计当前历史页），不叠加旧本机数字。
对局记录统一按时间排列：新结算的 `matchId` 关联本机与服务器记录，自己的结算行以服务器为准，本机队友等详情作补充；
旧记录没有可靠 ID 时不推测合并，只标注「仅此设备」，可用筛选查看。恢复码切换档案后，本机旧数据不会冒充新档案战绩。
本机格式 v2 添加可选 `matchId`，v1 记录原样保留并迁移，导入／压缩也保留 ID；旧客户端拒绝覆盖 v2 数据。
新服务器结算在本人 payload 中补充不含其他玩家的对局 frame；旧记录无需改库，缺少时长／隐秘核心信息时显示说明与破折号。
服务器战绩从启用后的新对局开始记录。服务器档案与最近历史按用户 ID 缓存在本机，暂时不可用时可读缓存及本机记录；
读取档案失败不会阻塞客户端开始流程，名称明确被拒绝仍按原规则阻止。


恢复码只显示新生成的原文，数据库只存哈希。重新生成使旧码失效，找回成功后码立即失效；
找回会在当前浏览器切换档案，不合并两份数据。已有其他设备仍保持登录。
切换档案时当前用户有进行中的对局则拒绝。清除浏览器数据、Cookie 到期或更换设备后，
没有恢复码的匿名档案无法自动找回；数据不会因此从服务器删除。

## 部署

需要支持 `node:sqlite` 的 Node 22.13+（本部署 Node 22.23.3 已核对支持）。
配置 `SP_USER_DB=/var/lib/stronghold-users/users.sqlite`，并将整个目录绑定到持久化宿主机路径。
服务仍可使用只读根文件系统，但这个目录必须可写，SQLite 的 WAL／SHM 文件也在这里。
本地开发可使用 `SP_USER_DB=.state/users.sqlite npm run dev`；`.state/` 不进入 Git。
未配置时旧有游戏、Redis 恢复和本机设置照常可用，档案入口仍可查看本机统计，不展示资料编辑和恢复码。
配置后若数据库无法打开或 schema 比代码新，启动失败，不降级为另一份空档案。

w2 用户数据挂载（2026-10-16 已启用，当前 UI 升级未部署）：

- 宿主机 `/mnt/user/compose/stronghold-protocol/users-data`
- 容器 `/var/lib/stronghold-users`，运行用户 `node`（UID/GID 1000）
- 首次部署前用 `install -d -m 700 -o 1000 -g 1000 <宿主机目录>` 准备目录。

数据库使用 WAL、FULL 同步及事务，文件权限 0600。单独的 Worker 持有连接，游戏线程不执行同步 SQL；
请求队列有上限，失败不打印 Cookie、恢复码、聊天、个人资料或 SQL 参数。
schema 用 `PRAGMA user_version` 管理，当前版本 1；将来的 schema 变更必须增加迁移并先备份。
每 24 小时通过 SQLite `VACUUM INTO` 创建一致备份，默认位于数据库旁的 `backups/`，保留最近 7 份。
这些备份与数据库在同一挂载中，异机备份另行配置。在线备份不能只复制主 `.sqlite` 文件而漏掉 WAL。

## 身份与权限

`userId` 是长期 UUID，`playerId` 和重连令牌仍属于可过期的游戏会话。
每个标签页可以有独立会话，设备通过恢复码共用个人档案，不复用同一个游戏连接。
随机 256-bit 凭证通过 HttpOnly、SameSite=Strict Cookie 保存；HTTPS 下添加 Secure，
有效期一年并在正常访问时续期。凭证只以 SHA-256 哈希存入 SQLite。

WebSocket 升级从 Cookie 关联档案；已关联档案的重连令牌不能被另一个档案或无身份连接接管。
用户 ID 和凭证不进入公开玩家列表。昵称须走原有名字审核；跨站请求被拒绝，
写接口只接受有限大小的同源 JSON，恢复码额外限流；客户端不能指定其他用户 ID 或上传服务器战绩。
旧客户端没有 Cookie 时仍能玩，但不自动拥有服务器个人档案。

HTTP（同源，无 CORS）：

| 方法 | 路径 | 内容 |
| --- | --- | --- |
| GET | `/api/user` | 读取／首次建立档案，设置 Cookie |
| POST | `/api/user/name` | `{name}`；明确更新昵称，自动重连不会覆盖服务器昵称 |
| POST | `/api/user/profile` | `{name, avatarId}`，头像只能是 `profile-avatars.json` 中的头像 ID 或 null |
| GET | `/api/user/stats?before=<cursor>` | 本人汇总和历史，每页 50 条 |
| POST | `/api/user/recovery` | `{}`；生成新的一次性恢复码 |
| POST | `/api/user/recover` | `{code}`；找回另一档案，换发当前设备凭证 |

战绩接口返回本人 `userId`、全量 `aggregate`、首屏 `matchIds` 及分页 `records`，客户端校验所属档案再更新缓存；
累计不依赖已加载的历史页数，缓存切换不能串用另一档案的数据。

## 结算与恢复

开启后每局生成独立 UUID，随 Match 检查点保存；PlayerState 的内部档案归属和头像也随检查点保存。
完整 Match Worker 的开局、恢复和结算走同一机制。
服务端结算回调写入自己的参与记录；`(game_id,user_id)` 为唯一键，重复结算、回放不会重复计数。
同一档案控制同局多个席位时只计一场。记录保留本人结算行，不能读取其他用户战绩。
房间代码复用不影响唯一性；暂时的重连身份和整个 Redis 状态键过期不删除用户档案／历史。
SQLite 写入是异步的，正常停服等待待写入任务；未提交的结算进入 Redis 快照中的 outbox，主动触发保存，失败保留并定时重试。重启后重放，事务唯一键去重。SQLite 已提交事务不受容器重建影响；未配置 Redis 时只有内存重试队列，不能保证尚未提交的结果抵御进程崩溃。

战绩来源是服务器结算，但当前部署的战斗由客户端模拟、`SP_VERIFY=off`；个人统计不等于防作弊排行榜。
未来要做竞技排名时须单独增强校验，不能把旧记录升级为已验证成绩。

Redis 继续负责房间／对局恢复，SQLite 负责长期个人数据，两份持久化目录都要保留。
当前修改增加可选字段，不改变游戏规则或对局快照版本；后续部署需要实际检查两个存储的联动。

## 原版个人头像库（待部署）

头像目录来自 [PRTS 个人头像一览](https://prts.wiki/w/个人头像一览)，记录页面修订 441454。
共 196 个：默认 15、特殊 83、活动 90、动态头像静态版本 8。选择器支持分类、名称／文件 ID 搜索，
每次展示 48 个，缩略图按需加载。按用户要求移除策略图标头像方案，不为旧 band ID 做转换或兼容；
未选择／未知头像显示原有默认形象，可重新选择并保存。名字独立更新不校验未修改的头像。

`data/profile-avatars.json` 记录名称、分类、原图来源、大小和 SHA-256；API 只接受该目录中的 ID。
原图下载到 `public/assets/profile-avatars/`，由本站提供，不从玩家浏览器请求 PRTS。
资源获取、可选预载「个人头像」组、逐文件哈希、CDN 重写及 ZIP 导入／导出复用原流程；
可选预载不受语音语言选择影响。首次准备或快速补齐用 `npm run assets:avatars`，完整流程仍用 `npm run assets`。
详见 [ASSETS.md](ASSETS.md) 的个人头像库部分。


## 0.3.0 统计与冷更新

博士档案的成就使用上游界面和共享统计模型；服务器从全部本人结算计算，历史分页不限制累计。
服务器保存玩法插件内容身份，默认排除玩法插件对局，可用“含插件对局”查看；纯外观插件不改变统计口径。
本机历史沿用上游 v2，并保留可选 matchId，不自动上传旧本机记录。

升级等待全部进行中对局结束和结算写入完成，再清理旧运行态；SQLite 身份、恢复码、头像与历史不清理。
同版本重启恢复不变，不要求跨版本进行中对局兼容。详见 [本次合并记录](MERGE_FORK_0.3.0.md)。
