# 后端多核与主线程优化（2026-10-17）

以下 10 月 17–18 日指标与默认策略来自 xinhai 上游，不能作为本服测量结果。本服 10 月 25 日合并保留 server.json 的 24h / 10s / 60s 策略；新增容量和采集配置见 [SERVER_CONFIG.md](SERVER_CONFIG.md)。待入库结算也按条分批传输，包含回放及伤害附件。

本次处理性能审查的第 3、4、6、7 项。不修改游戏规则、连接上限、完整对局 Worker 的默认开关或模拟池拓扑。

## 新对局分配

完整对局 Worker 每秒报告最近窗口的事件循环利用率、P99 额外延迟（扣除 20ms 采样间隔）、协作任务队列长度和服务器接管战场数。主线程结合房间数、待回复 IPC 计算分配分数，优先选择低负载的健康线程。超过 5 秒没有更新且仍有房间的线程按繁忙处理；尚未采样时使用房间数和待回复请求。已分配的对局不迁移。

`/metrics.matchWorkers.lanes[]` 新增 `load`、`loadAgeMs`、`score`。这些是调度信号，不是线程 CPU 时间测量；`pending` 仍不包含每局代理 Promise 链里尚未发出的操作。

## 状态增量

完整对局 Worker 在自己的线程里解析状态快照、计算差异并编码补丁。每局只保留每个流的最新快照；公共状态共享一个流，私人状态按玩家分流。IPC 保留原 JSON，额外带前后序号和可选补丁，不传重复状态对象。

主线程只核对连接已成功发送的基线是否匹配同一对局实例、流和前序号：匹配时转发补丁，否则包装全量 JSON。发送成功后才推进基线。新连接、重连、漏发、中间状态未收到、对局替换均可全量恢复；未协商增量的旧客户端继续收到原 JSON。普通本地主线程 Match 和插件 Host 沿用原传输路径。

## 检查点采集

持久化按所属完整对局线程分组，同组串行、默认最多四组并发。本地 Match 仍归为一个串行组。每个 Match 同时最多一个捕获请求，开局捕获与周期保存共享正在执行的请求。

每次等候捕获默认最多 2000ms；超时只跳过本轮该组剩余捕获，使用之前的安全检查点保存其他对局，不取消、重试或杀死正在执行的对局请求。后续保存复用未完成的捕获；原有对局 IPC 故障超时仍独立生效。并发分组较多时，整个采集轮次可能超过单次等候时间。晚到的旧 generation 不能覆盖同房间新对局的检查点。

`/metrics.persist.capture` 提供 `concurrency`、`waitMs`、`timeouts`、`oldestAgeMs` 和 `missing`。年龄以捕获开始时刻估算，恢复时用文档保存时间初始化，不是 Redis 最新成功落盘年龄。游戏战斗阶段本来就可能没有新安全检查点，应结合阶段判断。仍使用单个编码 Worker 和原 Redis 整份文档格式；没有引入存储分片，也没有按 dirty 状态跳过捕获。

## 插件与 CDN 清单

生产 `startServer` 使用后台插件扫描 Worker，启动时等待首份索引。请求读取已完成的索引快照，过期时合并触发后台检查；扫描完成后整体替换并通知监听者。变化可能在下一次请求中可见。失败保留上次索引，下次检查重试，不在主线程回退同步扫描。

工作台写入后的刷新明确等待扫描完成再返回结果和发出热更新事件。生产 registry 的 `refresh`、`rescan`、`setScriptHost` 返回 Promise，需要等待；独立工具和原同步 registry 默认 API 保持兼容。文件路径、白名单、真实路径及内容身份校验保持原逻辑。

CDN 清单缓存失效时，文件读取、JSON 解析、URL 重写和编码在专用按需 Worker 中执行，以独占缓冲传回。相同文件身份的并发请求共享一次编码，缓存命中直接复用正文；保持 GET/HEAD、缓存校验及无 CDN 时的原文件行为。正常关停关闭后台 Worker。

## 验证边界

针对性测试覆盖线程分配、状态补丁/重连/漏发/隐私边界、检查点并发/超时/旧 generation、后台扫描、工作台热更新、CDN 和监控。微基准：

```sh
node tools/server-hotpathsbench.mjs --matches 128 --lanes 4 --rounds 10 --checks 20
```

本机 i7-14700HX / Node v26.7.0 单次前后观察：状态转发主线程 ELU active 58.35 → 22.02ms；三次保存墙钟 294.65 → 87.60ms。ELU active 不是主线程 CPU 时间。测试为 INFO_CHECK、模拟连接和内存接收器，不包含真实战斗、Redis、TLS、公网或生产容量验收。

部署需要重启服务；本次没有部署、重启现网或开展 3000 人实战压测。

## 2026-10-18 存档回收与周期保存补充

本次用户快照为 1009 个对局、存档 67,186,924B、运行 15,434 秒、写入 5209 次，平均约 2.96 秒一次。最近十秒主线程 ELU 58.82%、P99 181.01ms、max 222.69ms，四个 Match Worker ELU 约 22%–24%；检查点超时和缺失均为 0。快照没有 recovery 分项，不能把整份 64.1MiB 都归为垃圾，也不能确认保存是每个尖峰的根因。

- 失败恢复仅在至少一名原真人身份仍在有效重连窗口内时保留；所有真人过期或离场后，加载和下一次保存均清除 recovery。新局替代旧局及历史 superseded 记录直接清除。有效但缺少插件/游戏数据的检查点保留，单人六小时、同盟十分钟；冻结墙钟断线时间，保存/重启不续期，不用模拟 savedAt 计算保留期。启动时在线的单人身份即使旧记录没有扩展字段，也按当前单人窗口恢复。
- 未变化的 recovery 对象在持久化 Worker 内缓存，主线程仅提交增删替换；线程故障后重新同步有效记录。JSON 格式及对局 generation 校验保留，不增加主线程整份编码。
- 按用户要求，周期检查及 Redis 写入默认由十秒延长至三十秒；开局立即捕获安全检查点，整份写入等待周期，不再因开局串联额外保存。显式 SP_REDIS_SAVE_MS 仍优先。正常退出先等已有保存，再捕获并写最后一份，随后才销毁房间和 Worker。原进程五秒退出兜底改为 SP_SHUTDOWN_TIMEOUT_MS 默认六十秒，超时以失败状态退出；容器停止宽限须大于此值。
- /metrics.persist 提供回收保留/分类删除计数、有效保存间隔、失败/跳过计数及最近一次保存的分段耗时。Exporter 提供 sp_persist_recovery_retained、sp_persist_recovery_removed_*_total、sp_persist_save_interval_seconds、sp_persist_last_*_seconds。postMs 为主线程提交序列化请求耗时，encodeMs 在 Worker，二者已包含于 serializeMs；capture/serialize/write 含等待，不能相加解释成主线程 CPU 或公网 RTT。

验证包含过期回收、有效数据缺失保护、重复重启不续期、Worker 缓存/故障恢复、三十秒定时、在途写入与最后存档，以及保存超过原五秒上限后才退出。部署须重启游戏服务并更新 exporter；本服保存周期继续为 10000ms；是否调整由运营配置决定。本轮未部署或验证线上尖峰下降。异常崩溃、强制结束和断电只能恢复最近成功写入的进度，三十秒周期扩大了这段耐久窗口。

## 2026-10-18 存档元数据分批传输

`metrics/202610181435metrics.json` 的最近保存：捕获 747.71ms、组装 7.74ms、主线程提交 51.14ms、Worker 编码 299.45ms、Redis 写入 71.59ms、整轮 1242.86ms，存档 42,497,656B。这里确认的连续同步工作是整包 `postMessage` 复制，其他异步阶段不能直接解释成主线程阻塞。该快照最近十秒 max 为 35.23ms，启动以来 max 为 1715.47ms，不能从单份样本断言历史尖峰都来自保存。

- 会话和房间改为每批最多八行，等待 Worker 确认后让出事件循环；Worker 负责拼装及整份编码。每次保存对 Session/Seat 共享配置建立临时引用表，减少跨批次重复复制；下一次保存重新读取，兼容恢复的可变旧结构，不引入按身份永久缓存的遗漏更新问题。
- 中途故障丢弃整轮，不在新 Worker 上继续半份元数据。已编码的最后成功快照使用发布后只读的 `SharedArrayBuffer`，Worker 重启按同一缓冲恢复，不在主线程克隆整份字节。失败写入不推进重播种子。Redis 仍写相同 UTF-8 JSON，格式、键、TTL 和退出保存顺序不变。
- 分批期间较新的 Match generation 不混入旧元数据，也不被旧快照的清理删除；下一次保存继续使用它的检查点。原本的旧 generation 防覆盖规则保留。
- `timing.postMs` 现在是全部批次同步提交之和，`postMaxMs` 是最长单次提交，`postBatches` 是提交次数，线程创建也计入提交。批次打包及 GC 不计入提交计时；主线程仍组装元数据、使用 Redis 客户端发送整份字节，未宣称全部保存工作已移出主线程。单条很大的资料、有效 recovery 首次同步及其他负载仍可能造成尖峰。

本地复现：`node tools/persistbench.mjs --metadata`，合成 3000 会话、1000 房间、300 项配置/人，JSON 86,020,604B，不包含 Match 捕获、真实战斗、Redis、TLS 或公网。三轮修改前提交 168.72–183.64ms，心跳最大间隔 168.94–183.79ms；最终实现单次最长提交 1.18–1.55ms、心跳最大间隔 16.02–16.89ms，整轮 498.36–527.68ms（原实现 549.75–567.71ms）。心跳由本机 1ms 定时器观察，受平台定时器精度影响；这些是单机微基准，不能推断生产容量或承诺线上尖峰消失。部署需重启游戏及更新 exporter，再对照相近负载下的 postMaxMs、事件循环近期窗口和写入计数。
